# 設計: MoeSpeech からアライメント済みマニフェストまで

作成日: 2026-08-28 / 対象ブランチ: `japanese-model-training`

## 何のための文書か

日本語モデルの検証ラン（フェーズ1）は、`data/ja/train_aligned.jsonl` が無いと開始できない。
アライナに渡すものが存在しないためである。本文書は、MoeSpeech の zip から
そのマニフェストを作るまでの設計を定める。

**実行環境は vast.ai 上**（[vast.ai 学習制約](#前提)参照）。前処理も学習も
すべてクラウド側で行い、手元には成果物の jsonl だけを持ち出す。

## 実測: `info.csv` が DL 前に答えを与えた

`ayousanz/moe-speech-plus` のトップレベルに `info.csv`（12.5 KB）があり、
**473キャラ全ての `num_files` / `total_duration_min` / `f0_mean` を持つ**。
音声を1バイトも落とさずに規模と選定を決められる。

| 項目 | 実測 |
|---|---|
| 規模 | 473キャラ / 395,170ファイル / **621時間** |
| キャラ別の平均クリップ長 | 中央値 **5.8秒**、最大 9.8秒、最小 2.6秒 |
| 平均8秒以上のキャラ | **473中27** |
| f0 平均 | 中央値 290 Hz、**200 Hz 未満は473中95** |
| 目標124時間に必要なキャラ数 | **大きい順に28キャラ** |

この3つが設計を決めた。

### 決定1: 連結は必要（測って確定した）

キャラ別の平均クリップ長の中央値が 5.8 秒。`training/dataloader.py` の
`MIN_CUT_SEC = 1.0` はカット点の前後に1秒ずつを要求するので、ターゲットに残るのは
平均4.8秒未満になる。**平均8秒以上のキャラは473中27しかない**ため、
「長いクリップだけ選べば連結を回避できる」という道は無い。

同一キャラのクリップを連結して擬似長尺ファイルを作る。英語パイプラインが
章まるごとの mp3 に `start`/`duration` で窓を張っているのと同じ形であり、
`Entry.start`（`dataloader.py:34`）が既にその形を受け付ける。

### 決定2: キャラは大きい順に取る（DL 量が 1/6 になる）

当初の記録は「約160キャラ / 30 GB で約123時間」だったが、これは
キャラを無作為に取る前提だった。`total_duration_min` の降順に取ると
**28キャラで124時間**に届く。zip の個数が 1/6 以下になり、DL も展開も速い。

話者の多様性は減るが、検証フェーズの目的は「パイプラインが正しいか」の切り分けであり、
話者数ではない。本番フェーズでは選定基準を変える（後述）。

### 決定3: ドメインの偏りを数値として記録する

f0 平均の中央値が 290 Hz、200 Hz 未満は 2 割。アニメ／ギャルゲ由来なので当然だが、
**男性話者が構造的に少ない**ことは、モデルの性質として記録しておく必要がある。
検証フェーズでは是正しない（変数を増やさない）。

## スクリプトの構成

`training/scripts/prepare_moespeech.py` を1本作る。
`training/scripts/prepare_data.py` と同じ規約に従う:

- typer CLI、`--` オプションで各ステージのパラメータを受ける
- **各ステージは出力が既に存在すればスキップする**
- 途中で死んでも同じコマンドの再実行で続きから進む
- 部分的な出力は `.partial` に書き、完了時に rename する
  （中断で生まれた半端なファイルを「完成済み」と誤認しないため）

**再開可能性は vast.ai では必須**である。インスタンスは preemption と destroy で
消えるため、「最初からやり直し」が常に選択肢から外れていなければならない。

### ステージ

| # | ステージ | 入力 → 出力 |
|---|---|---|
| 1 | `select-characters` | `info.csv` → `characters.json`（DL 不要） |
| 2 | `download` | 選ばれた zip のみ取得 |
| 3 | `extract` | zip → キャラ別ディレクトリ |
| 4 | `probe` | 各 JSON → `probe.json`（長さ分布・相互CER・speechMOS） |
| 5 | `select-utterances` | 閾値適用 → `utterances.jsonl` |
| 6 | `group` | 同一キャラを連結 → 擬似長尺 WAV + `start`/`duration` |
| 7 | `manifest` | → `train.jsonl` / `valid.jsonl` |
| 8 | `align` | → `train_aligned.jsonl` / `valid_aligned.jsonl` |

ステージ2はキャラ単位で完結するので、キャラ数を増やして再実行しても
既に落としたものは再利用される。ステージ8は
**`prepare_data.py` の `align()` をそのまま呼ぶ**（`:72`）。あの関数は既に
マニフェストと出力パスを取り、`.partial` → rename で再開可能な形になっている。
実装し直さない。

## 24 kHz 変換は行わない

`training/dataloader.py:59` の `_load_window` は読み込み時に
`convert_audio` でリサンプルする。当初の見積りに含めていた
「24 kHz 変換」の工程は**不要**であり、落とす。

44.1 kHz のまま保持することには積極的な理由もある: 音響品質の上限を決めるのは
このサンプルレートであり、フェーズ3（仕上げ）は MoeSpeech のみで行う設計になっている。

## 転写の選択とフィルタ

各音声に同名の JSON があり、2系統の ASR 転写を持つ:

- `anime_whisper_transcription` — litagin/anime-whisper
- `parakeet_jp_transcription` — nvidia/parakeet-tdt_ctc-0.6b-ja

加えて `duration` と `speechMOS`（UTMOS v2）がある。

**採用する転写と閾値は、この文書では決めない。** 相互 CER と speechMOS の分布は
zip を1つ展開しないと測れないためである。ステージ4がそれを測り、その実測から
ステージ5の既定値を決める。**測る前に閾値を書くのは、この計画が排してきた
「根拠のない数値」そのものになる。**

ステージ4が出力すべき統計:

- クリップ長のヒストグラム（連結の設計が妥当かの再確認）
- 2系統転写の相互 CER の分布
- `speechMOS` の分布
- 各閾値で何％が残るかの表

`training/README.md` は「音響は良いのに transcript に従わない場合は転写が不正確」
「手動転写を優先せよ」と述べている。手動転写は存在しないので、
**相互 CER が実質的な転写品質の代理指標**になる。

## 連結の設計

同一キャラのクリップを結合して1本の WAV にし、各発話は
`{"path": <連結WAV>, "start": <秒>, "duration": <秒>}` で指す。

- **キャラを跨いで連結してはいけない。** 連結ファイル内のどこで切っても
  同一話者であることが、voice prompt とターゲットの話者一致の前提になる。
- 発話の間に無音を挟むかは実装時に決める。挟まない場合、連結点が
  アライナには単なる発話境界に見える。
- 1本あたりの目標長は 60〜120 秒程度（`max_duration_sec` の既定 30 秒より十分長く、
  ファイル数が爆発しない範囲）。実装時に確定する。

## train / valid の分割

**話者単位で held-out する。** `prepare_data.py` が章単位で held-out を作るのと
同じ考え方（`:204` の `held_out`）。

評価プロトコルは「ある発話で声をクローンし、別の発話を合成する」形なので、
valid 側の話者には**複数の発話が必要**である。発話単位で無作為分割すると
この条件を満たさない組が生まれる。

valid の規模は 1 時間程度（`prepare_data.py:218` が「valid split が空にならないよう
常に約1時間を確保する」としているのに倣う）。

## アライメント

```
--model vumichien/wav2vec2-large-xlsr-japanese-hiragana
--segmenter japanese
```

`align_data.py:402-409` は、`--segmenter japanese` に対して**ひらがなを語彙に持たない
モデルを拒否する**ガードを持つ。上記チェックポイントは 82 のひらがな＋長音記号を持つ
（`training/tests/test_align_data.py:80` に記録）。

日本語 CTC モデルは GPU で回すため、この工程も vast.ai 上で行う。

## 成功の判定

このスクリプトの成果物が正しいかは、以下で判定する:

| 判定 | 方法 |
|---|---|
| マニフェストが loader に読める | `DataLoader` で数バッチ回す |
| 連結が話者を跨いでいない | 各連結ファイルの発話が単一キャラ由来であることを検査 |
| `start`/`duration` が正しい | 無作為に選んだ発話の音声長と `duration` の一致 |
| アライメントの成功率 | `align_data` が報告する ok/skipped の比 |
| カット可能率 | `words` が2語以上でタイムスタンプを持つ発話の割合 |

**最後の2つが低い場合、原因は音声ではなく転写かアライナの選択にある。**
その切り分けはステージ4の統計に戻って行う。

## 範囲外

| 項目 | 理由 |
|---|---|
| GOL データセットの取り込み | 検証フェーズは MoeSpeech 単独（変数を減らす） |
| 学習の起動と go/no-go 判定 | マニフェストの中身を見てから設定を決める |
| 本番フェーズのキャラ選定 | 検証の結果次第。話者数と多様性の基準が変わる |
| 話者クラスタリング | GOL 用。MoeSpeech はキャラ別フォルダがあるので不要 |

## 前提

- 実行は vast.ai 上。手元マシンは調査・コード・文書のみ
- 学習中のチェックポイントは退避せず、インスタンス上に置く
- HF に上げるのは最終モデルのみ（gated / manual approval）
- MoeSpeech は情報解析利用のみ許諾。**重みの公開は問題ないが、音声ファイルの
  再配布は不可**。公式モデルはそもそも音声を同梱していないので、
  公式の作法に従えばこの制約は発生しない
