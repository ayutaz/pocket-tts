# 設計: GOL の取り込みとフェーズ2

作成日: 2026-08-30 / 対象ブランチ: `japanese-model-training`

## 何のための文書か

フェーズ1（検証ラン）は合格した。パイプラインは正しく、モデルは日本語の音韻を獲得する。
次は品質を問うフェーズだが、そこには**未実装のものが1つある** — GOL の取り込みである。
現在の `prepare_moespeech.py` は名前の通り MoeSpeech 専用で、GOL を1行も扱えない。

本文書はその設計を定める。**実行は全て vast.ai 上**で、手元のディスクや回線は設計を縛らない
（2026-08-30 のユーザー決定）。

## 実測: `metadata.tsv` が音声ゼロで答えを与えた

MoeSpeech で `info.csv`（12.5 KB）が果たした役割を、GOL では `metadata.tsv`（1.68 GB）が
果たす。7 TB を1バイトも落とさずに全件を集計でき、**README の3つの数字と完全に一致した**。

| 項目 | 実測 |
|---|---|
| 規模 | **7,405,094 発話 / 19,349話者 / 10,654時間** |
| 形式 | **48 kHz 32bit mono**、0.66 GB/時間 |
| 構造 | `<game_id>/<speaker>/<file>.wav`。**740万行中、破れ0件** |
| クリップ長 | 中央値 **4.55秒**、平均 5.18秒（MoeSpeech は 5.46 / 6.00） |
| DL 単位 | `<game_id>.tar` = 1作品。中央値 **17.4時間・35話者** |
| 転写 | `text` 列1系統。「。。」を含む行は **612 / 740万（0.01%）** |

### 話者分布は額面通りに読めない

| | |
|---|---|
| 1話者あたり時間の中央値 | **0.6分** |
| 1時間以上の話者 | **2,095人**（計 9,493時間 = 全体の89%） |
| 発話が1つだけの話者 | 3,922人 |

**19,349という数字を前提に設計してはいけない。** 実質は約2,000人で、その2,000人が9割を持つ。
話者単位の held-out もこの集合から取る。

### tar を大きい順に取ったとき

| 目標 | tar | 話者 | 容量 |
|---|---|---|---|
| 500時間 | 7 | 1,161 | 330 GB |
| 1,000時間 | 18 | 2,451 | 660 GB |
| 2,000時間 | 45 | 4,768 | 1.3 TB |
| 5,000時間 | 154 | 12,143 | 3.3 TB |

## 訂正: エポック数の見積りが間違っていた

フェーズ1の報告で「本番は約1.5エポックになるので過学習は消える」と述べたが、**誤りである。**
発話数で計算し直すと（GOL は 695発話/時間）:

| GOL 時間 | 総発話数 | 250k step でのエポック |
|---|---|---|
| 1,000 | 745,217 | **21.5** ← フェーズ1の19.5より多い |
| 2,000 | 1,440,270 | 11.1 |
| 5,000 | 3,525,429 | 4.5 |
| 全量 10,654 | 7,455,258 | 2.1 |

**エポック数だけを根拠にするなら、GOL をほぼ全量取ることになる。** だがそれは 7 TB の
ダウンロードと 5,000 GPU-h 級のアライメントを意味する。先に確かめるべきことがある。

## 決定1: 品質フィルタはアライメントスコアにする

GOL には ASR が1系統しかない。フェーズ1を支えた**相互 CER が使えない**、これが取り込みで
新しく設計すべき最大の項目である。

候補は3つあった。

| 案 | 費用 | 問題 |
|---|---|---|
| 2つ目の ASR を自前で回す | 2,000時間で40〜80 GPU-h（$80〜160） | 学習本体に匹敵する費用 |
| speechMOS を自前計算 | 中程度 | **フェーズ1で反証済み** — UTMOS は朗読音声で較正されており、同じくビジュアルノベル由来の GOL でも中央値が低く出るはず。指標とドメインのずれを測ることになる |
| **アライナのスコアを使う** | **ゼロ** | 実装が要る（後述） |

**3つ目を採る。** `align_data.py` の Viterbi は `trellis[b, t_end, n]` に
「音声がそのテキストを支持する対数確率」を持っているが、現状は
**「整列不能か」の判定にだけ使って捨てている**（`:100`）。これを出力すれば、
**転写と音声の一致度そのもの**が、追加の計算ゼロで全発話について手に入る。

相互 CER が「2つの ASR が食い違う場所」という**間接的な**代理指標だったのに対し、
これは**直接的**である。MoeSpeech にも同じ指標が使えるので、2つのコーパスを
同じ物差しで扱えるようになるという副次的な利点もある。

**閾値はここでは決めない。** 分布を測ってから決める —— フェーズ1で
`--min-mos 3.0` を事前に書いていたらコーパスの8分の7を黙って捨てていた、という
経験がそのまま当てはまる。

### 順序が変わる

スコアはアライメント後にしか得られないので、フィルタの位置がフェーズ1と変わる。

```
フェーズ1:  選定(CER/MOS) → 連結 → マニフェスト → アライメント
フェーズ2:  粗い選定 → 連結 → マニフェスト → アライメント → スコアで絞る → 学習用マニフェスト
```

アライメント済み jsonl を後から絞る形になる。**アライメントは捨てる分にも走る**が、
2つ目の ASR を回すよりはるかに安い。

## 決定2: 段階を分け、M2a が「量か多様性か」を決める

フェーズ1の過学習には原因が2つありえた。**19.5エポック**と**27話者**である。
どちらが支配的かは分かっていない。そして答えによって必要な GOL の量が変わる。

- 話者数が支配的なら、1,000時間（2,451話者、91倍の多様性）で足りる
- エポック数が支配的なら、5,000時間以上が要る

**M2a はこれを測るための実験として設計する。**

| | M2a（中間検証） | M2b（本番） |
|---|---|---|
| データ | GOL 1,000時間 + MoeSpeech 87時間 | M2a の結果で決める |
| step | **20,000**（745k発話に対し 1.7エポック） | 250,000 |
| 目的 | GOL 取り込みの検証 + **valid が turn するか** | 品質 |
| 費用 | 約$15〜25 | $75〜145 |

M2a を 20k step で止めるのではなく、**valid が上向くまで、あるいは 40k step まで回す**。
フェーズ1が壊れた19.5エポックに達するのは 745k発話では 232k step なので、M2a の範囲では
エポック数は問題にならない。**それでも valid が turn するなら、原因は話者数ではない**。

## 決定3: 選定は tar 単位、そのあと話者で絞る

MoeSpeech は「zip = 1キャラ」だったので選定単位と話者が一致していた。GOL は
「tar = 1作品 = 約35話者」なので二段になる。

1. `metadata.tsv` から tar を大きい順に選び、目標時間に届くまで取る（音声不要）
2. 展開後、**発話が2つ未満の話者と、合計が閾値未満の話者を落とす**

2つ目が要るのは、中央値0.6分という分布のためである。1発話しかない話者は
評価に使えず（声をクローンして別の発話を合成できない）、連結もできない。

## 決定4: valid は複数話者にする

フェーズ1の valid は1話者だった。その loss は step 7,500 で底を打ち2倍に悪化したが、
**それを「モデルの悪化」と読むのは誤りだった** —— `train.py:244` はサンプルの
voice prompt を学習バッチから取るので、サンプルは「見た声」を、valid は「見ていない1人」を
測っていた。耳の判定は 15,000 の方が良く、両方とも正しかった。

ボイスクローンが売りのモデルでは**未知話者側の数値が本質**であり、1人では何も言えない。
**M2a では最低20話者を held-out する。** `--valid-hours` を上げるだけで届く
（1,000時間・2,451話者なら、20話者は約8時間）。

## 決定5: `num_ckpt_keep` を増やす

フェーズ1では valid 最良の step 7,500 が、記録を見る前に削除されていた
（`ckpt_freq: 2500` × 3世代）。M2a/M2b では保持数を増やす。

## スクリプトの構成

`training/scripts/prepare_gol.py` を1本作る。`prepare_moespeech.py` と同じ規約に従う
（typer CLI、各ステージは出力が在ればスキップ、`.partial` → rename、再開可能）。

| # | ステージ | 入力 → 出力 |
|---|---|---|
| 1 | `select-games` | `metadata.tsv` → `games.json`（音声不要） |
| 2 | `download` | 選ばれた tar のみ取得 |
| 3 | `extract` | tar → `<game_id>/<speaker>/` |
| 4 | `select-speakers` | 発話数・合計時間で話者を絞る → `speakers.json` |
| 5 | `select-utterances` | 長さの範囲で絞る → `utterances.jsonl` |
| 6 | `concatenate` | 同一話者を連結（`prepare_moespeech.concatenate` を**再利用**） |
| 7 | `manifest` | → `train.jsonl` / `valid.jsonl`（`split_by_speaker` を再利用） |
| 8 | `align` | → `*_aligned.jsonl`（**スコア付き**） |
| 9 | `filter-by-score` | スコア分布を測り、閾値で絞る → 学習用マニフェスト |

**ステージ6・7は `prepare_moespeech.py` の関数をそのまま呼ぶ。** `concatenate` は
話者混在を拒否し、`split_by_speaker` は話者単位で held-out する —— どちらも
コーパスに依存しない。実装し直さない。

**2つのコーパスの合流点はステージ7**である。MoeSpeech 側の `entries/*.jsonl` と
GOL 側のそれを結合してから分割する。

## 成功の判定

| 判定 | 方法 |
|---|---|
| GOL のマニフェストが loader に読める | `DataLoader` で数バッチ |
| 連結が話者を跨いでいない | `concatenate` のガード（既存） |
| アライメントの成功率 | `align_data` の ok/skipped |
| **スコア分布が意味を持つ** | 低スコアの発話を抜き出し、転写と音声が実際に食い違うか目視・聴取で確認 |
| **valid が turn するか** | 20話者以上での valid loss 曲線。**M2a の主目的** |

## 範囲外

| 項目 | 理由 |
|---|---|
| M2b の量の決定 | M2a の valid 曲線を見てから |
| 蒸留（フェーズ4） | 24層のまま評価できる |
| サンプルボイスの用意（フェーズ5） | MoeSpeech からは作れない。別途 |
| GOL の 48 kHz を活かす仕上げ工程 | フェーズ3の話。ただし「仕上げは MoeSpeech のみ」の根拠は消えた |

## 前提

- 実行は**全て vast.ai 上**。ディスクは借りる判断であり、設計を縛らない
- 学習中のチェックポイントは退避しない
- HF に上げるのは gated（manual）
- GOL のライセンスは確認済みで問題なし。MoeSpeech は情報解析利用のみ許諾で、
  **重みの公開は可、音声の再配布は不可**
